# Gym FAQ RAG: pipeline

A retrieval-augmented FAQ chatbot for gym, training and nutrition questions. It follows Walert's `data -> index -> retrieve -> evaluate` pipeline, and answers only from our own knowledge base, with citations.

- **Retrieval:** BM25 (Pyserini `LuceneSearcher`, real Anserini/Lucene) and dense search (all-MiniLM-L6-v2 with a FAISS index), combined with Reciprocal Rank Fusion (RRF).
- **Generation:** a small local open-source model, `Qwen2.5-1.5B-Instruct`, instead of Walert's Falcon-7b. Same idea (self-hosted, free, no API key), but sized to run on a normal CPU.
- **Guardrails:** off-topic and wrong-format requests are refused, weak matches return "not covered", and replies are checked for citations and invented numbers.

## Layout

```
data/
  collection.csv         40 passages from 11 sources (id, text, source)
  topics.csv             37 test questions across 24 topics
  groundtruth.csv        which passages answer which topic, relevance 1 or 2
  topic_groups.csv       topic_id -> known/inferred (10 known, 14 inferred topics)
  qrels.txt              generated by data_prep.py
  collection_jsonl/      generated by build_index.py (JsonCollection format for Anserini)
src/
  app.py                       chatbot web interface
  data_prep.py                 builds qrels.txt from topics.csv + groundtruth.csv
  build_index.py               converts collection.csv -> JSONL, builds the Lucene (BM25) index
  build_dense_index_pyserini.py  builds the dense FAISS index (MiniLM, normalised vectors)
  retrieval.py                 BM25 run: topics.csv -> target/runs/bm25.txt
  dense_retrieval.py           dense run: topics.csv -> target/runs/dense.txt
  hybrid_retrieval.py          RRF run: topics.csv -> target/runs/rrf.txt
  eval.py                      scores a run against qrels.txt with ranx (known/inferred split)
  custom_eval.py               custom retrieval metrics: Top-1, MRR, Hit Rate @ 5, Precision @ 5
  answer_eval.py               answer-level metrics: runs every question through the chatbot
  chatbot.py                   the hybrid FAQ chatbot (BM25 + dense + RRF + local Qwen answer)
target/
  indexes/bm25/                the Lucene index
  indexes/dense_pyserini/      the dense FAISS index
  runs/                        retrieval run files (bm25.txt, dense.txt, rrf.txt)
  answer_eval.csv              per-question answer-level results
requirements.txt
```

## Setup

Requires a JVM (Java 11+) for Anserini/Lucene. Install a JDK (`pacman -S openjdk-21-jdk` on CachyOS/Arch, or the equivalent for your OS).

```bash
pip install -r requirements.txt
pip install sentence-transformers faiss-cpu   # if not already in requirements.txt
export OPENAI_API_KEY=unused
```

The `OPENAI_API_KEY` line is a Pyserini workaround, not a real key. One of its internal modules touches an OpenAI client at import time even though this project never uses OpenAI, and it crashes if the variable is not set. Any dummy value works. Our scripts also set a dummy value themselves.

No real API key or paid service is used anywhere in this pipeline.

On first run, `chatbot.py` downloads its free model (`Qwen2.5-1.5B-Instruct`, about 3 GB) and the MiniLM encoder from Hugging Face. This needs internet access once, and after that it runs fully offline on CPU.

`pyserini` pulls in `torch` and `transformers` because of how the package is structured. This is not something this project adds on top.

## Run the pipeline

```bash
cd src

# 1. Build the qrels
python data_prep.py                                  # data/qrels.txt

# 2. Build the indexes (re-run when collection.csv changes)
python build_index.py                                # target/indexes/bm25/
python build_dense_index_pyserini.py                 # target/indexes/dense_pyserini/

# 3. Run the three retrieval methods
python retrieval.py                                  # target/runs/bm25.txt
python dense_retrieval.py                            # target/runs/dense.txt
python hybrid_retrieval.py                           # target/runs/rrf.txt

# 4. Evaluate retrieval
python eval.py all ../data/qrels.txt ../target/runs/bm25.txt
python eval.py known ../data/qrels.txt ../target/runs/bm25.txt
python eval.py inferred ../data/qrels.txt ../target/runs/bm25.txt
python custom_eval.py ../data/qrels.txt ../target/runs/bm25.txt ../target/runs/dense.txt ../target/runs/rrf.txt

# 5. Evaluate full answers (loads the chatbot, takes a few minutes on CPU)
python answer_eval.py                                # target/answer_eval.csv
```

The query encoder in `chatbot.py`, `dense_retrieval.py` and `hybrid_retrieval.py` uses mean pooling and normalised vectors (`pooling="mean", l2_norm=True`). This must match how `build_dense_index_pyserini.py` builds the index. If you change one, change all of them and rebuild the dense index.

## Results

### Retrieval (37 questions)

```
| Model / Run File       | Direct FAQ Top-1 Acc | Mean Reciprocal Rank | Hit Rate @ 5 | Precision @ 5 |
| ---------------------- | -------------------- | -------------------- | ------------ | ------------- |
| bm25.txt               |               81.82% |               90.77% |      100.00% |        32.43% |
| dense.txt              |               81.82% |               94.59% |      100.00% |        33.51% |
| rrf.txt                |               90.91% |               94.14% |      100.00% |        33.51% |
```

1. **Direct FAQ Top-1 Accuracy:** how often the main answer lands at rank 1 for the known-topic questions.
2. **Mean Reciprocal Rank (MRR):** where the first correct passage appears. It heavily penalises drops down the list.
3. **Hit Rate @ 5:** how often a correct passage appears in the top 5, ignoring order.
4. **Precision @ 5:** how much of the top 5 is useful rather than noise. Most topics have only one or two relevant passages, so about 33% is close to the ceiling.

The final chatbot uses RRF. It has the best Top-1 accuracy, but the gap to BM25 and dense is one question out of 11 known-topic questions, so it is not a strong claim.

### Answer level (37 in-scope questions, full chatbot)

| Measure                                                | Result |
| ------------------------------------------------------ | ------ |
| Answered                                               | 94.6%  |
| Unanswered ("not covered")                             | 0.0%   |
| Refused by a guardrail                                 | 5.4%   |
| Model cited a passage by itself (of answered)          | 40.0%  |
| Correct passage in the retrieved context (of answered) | 100.0% |
| Cited passage was a correct one (of answered)          | 88.6%  |
| Average word support (faithfulness proxy)              | 64.8%  |
| Off-topic questions declined                           | 8 of 8 |

### Known limitations

- The test set is small (37 questions, 11 known-topic questions), so one question moves Top-1 by about 9 points.
- If the model forgets to cite, the chatbot adds `[1]` itself. This happened for 60% of answers, so the "cited a correct one" figure is flattered by those automatic citations.
- Word support only checks that the answer's words appear in the retrieved passages. It is a rough proxy, not true faithfulness, and needs a manual check of a sample.
- Most off-topic test questions were caught by the blocked-word list rather than the score thresholds, so the thresholds are tested lightly.
- The numeric guardrail can refuse a correct answer, for example when the number comes from a source name rather than the passage text.
